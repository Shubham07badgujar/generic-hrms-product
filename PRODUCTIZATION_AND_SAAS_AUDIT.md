# Productization and SaaS Audit

What this product was, what it is now, and what is still missing. Written at
commit `cd8932f` on the `saas/multi-tenant` branch, against the code rather
than against the plan — where the two disagree, the code is what this records.

Companion documents: [`TENANT_ISOLATION_TEST_REPORT.md`](TENANT_ISOLATION_TEST_REPORT.md)
is generated by the attempts it describes; [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
PART 13 is the design record; this file is the audit.

---

## 1. The fact that shaped everything

**This codebase was multi-tenant, and tenancy was torn out after a cross-tenant
breach.** Incident HRMS-INC-20260717-01: tenant context was established in
Django middleware, before DRF resolved a token-authenticated user, so the
context variable stayed unset and the tenant manager **failed open**, returning
rows across organizations. A user in one organization approved and locked
another organization's payroll run.

So this was not a greenfield tenancy build. It is a rebuild of a mechanism that
already failed here, and it is judged on whether it defeats that specific
failure mode.

The incident was an **ordering bug**: tenant identity lived in an ambient
variable that had to be *set* before it was *read*. The response is not "set it
more carefully" but to remove the precondition — read-path tenant identity is
derived from the resolved principal, inside the same function that already
decides what that principal may do.

## 2. Where the product started

| Metric | At the baseline |
|---|---|
| Backend | ~74k LOC, 18 apps, 96 models, 55 router ViewSets, 119 custom actions |
| Frontend | ~40k LOC, React 18 + TypeScript, 45 routes, 13 feature directories |
| Tests | 1,273 backend, 251 frontend |
| Models with an organization column | 0 — `README.md` rule #1 was "do not add an `organization` FK" |
| Queryset call sites | 509 total, 412 runtime: **257 in `services/`**, 115 in `api/` |
| Service functions taking an actor | 126 of 386 |
| Writable relational serializer fields with unfiltered querysets | 77, across 83 `ModelSerializer`s |

Two of those numbers decided the architecture. **257 service-layer queryset
sites, with only a third of service functions receiving an actor**, meant
threading an explicit `organization=` argument through services was not viable.
And **77 writable relational fields** meant the likelier hole was *writes*, not
reads — which turned out to be exactly right (§6).

## 4. The tenancy model

**The backend determines the organization. The client never does.**

```
JWT / authenticated User  →  OrganizationMembership  →  resolved Organization
```

An `organization_id` in a query string, body, path segment or header is never
trusted as tenant identity. This extends to related-object ids: a payload
naming another organization's department, manager, job opening or location is a
validation error, not a silent cross-tenant write.

**Every organization-owned table carries the column** rather than resolving an
organization through a relationship. That is a deliberate denormalization: with
the column everywhere the predicate is one literal string, so no per-model path
can be mistyped into an open filter, and the build check becomes decidable
("does this model have the column?") instead of a path-validation exercise.
Drift is closed on the write path — a derived model names its parent in
`org_source` and `save()` copies the organization from it, so a Payslip cannot
disagree with its PayrollRun.

**The five global tables**, each for a stated reason:

| Table | Why it is not tenant-owned |
|---|---|
| `accounts.User` | Login identity is global: email is the `USERNAME_FIELD` and must be unique platform-wide. A user's tenant comes from their membership. |
| `organization.Organization` | Is the tenant. |
| `organization.OrganizationMembership` | Resolving a principal's organization is what this table is queried *for*, so requiring one first would be circular. |
| `platform.Plan` | A description of what the SaaS offers, shared by every customer on it. |
| `statutory.StatutoryRuleSet` | PF/ESI/PT/income-tax tables are facts about the Republic of India, not about a customer. Duplicating them per organization would mean N copies to verify and would defeat four-eyes verification. |

`audit.AuditLog` carries a **nullable** column. The predicate is `= X`, never
`= X OR IS NULL`, so platform events stay invisible to organization users
without a special case — and the dangerous shape is one nobody has to remember
not to write.

## 5. How it is enforced

Five layers, each catching what the others cannot.

| Layer | What it covers | How it fails |
|---|---|---|
| **A. Organization predicate** in `scope_queryset()`, applied *before* the `Scope.ALL` early return | every read through the view mixins and ~15 direct callers | `.none()` |
| **B. Fail-closed manager** on every organization-owned model | the 257 service sites, Celery, management commands, and DRF's auto-generated relation querysets | **raises** `OrgContextMissing` |
| **C. Serializer relation scoping** (`ScopedRelationsMixin`) | writable relational fields, deliberately rather than by accident | 400 |
| **D. Build-time checks** (`access.E001`–`E017`) | code that does not exist yet | fails `manage.py check`, therefore CI and boot |
| **E. Database composite foreign keys** | raw SQL and bulk paths | **not implemented** — see §12 |

Two earn their keep above the rest. **B**, because two thirds of the queryset
surface is in services, and **D**, because it is the only layer protecting code
not yet written.

**Layer B raises rather than returning `.none()`.** The mirror image of failing
open is failing *silently*: an empty queryset in a Celery task is
indistinguishable from "no work to do", so the bug survives until somebody
audits rows that should have changed. An exception is the only failure mode a
developer cannot ignore.

**Layer B is unconditional.** It shipped behind a per-app `STRICT_TENANT_APPS`
set, because flipping an app changes the default behaviour of every query in it
at once and the fallout had to be read in reviewable pieces. All fifteen apps
completed that rollout and the set was **deleted rather than left standing at
"everything"** — an opt-in whose only correct answer is "yes" is a step someone
can forget, and forgetting it does not fail: it produces a new model that
quietly returns every customer's rows. `access.E017` fails the build for an
organization-owned model whose manager does not filter, which is the remaining
way it could be lost (`objects = models.Manager()` on a model that otherwise
looks protected).

**Deliberately rejected:** tenant-resolving middleware (that *is* the 2026
architecture); schema-per-tenant (same "must be set first" property, and the
failure was in the application layer); per-tenant field encryption keys (the
key is process-wide, so per-org keys buy the appearance of isolation and none
of the substance); Postgres RLS **for now** (genuinely the strongest layer, but
`CONN_MAX_AGE=60` reuses connections and `ATOMIC_REQUESTS=False` leaves no
natural boundary for `SET LOCAL`, so a half-implementation *causes* the leak it
prevents — the uniform column layout keeps it addable later).

## 6. What the conversion found

Every one of these was a live cross-tenant defect in a system whose test suite
was green. They are listed because an audit that records only what passed is
advertising.

| Defect | Effect before the fix |
|---|---|
| Relation ids in custom endpoint bodies | `POST /exits/` offboarded **another organization's employee**: status set to resigned, login and mailbox flagged, a settlement created, the audit row stamped to the attacker's organization. `/resignations/` was exploitable the same way. 23 declared relation fields across 16 serializers accepted foreign ids. |
| Payroll run location | `POST /payroll/runs/` read `location` by hand, so relation scoping never saw it. One organization's run was created carrying another's location, and the response echoed its code. |
| Authority from anywhere | Permissions were built from a user's role grants in **every** organization. One Admin grant row planted elsewhere made an ordinary employee an Admin at home, and the admin sign-in door issued them a token. |
| Retention purge | `purge_candidates --organization <slug> --apply` anonymised **every** organization's overdue candidates; `repair_application_stages` moved another company's applications and wrote repair events into its history. |
| Unaudited updates | The audit trail re-read a row through the tenant manager before an update. With another organization bound it found nothing, so the update was silently **never audited**. |
| Audit log reads | One organization's admin could read another's audit trail through `/api/v1/audit/<id>/` — a resource the brief names by name. |
| Scheduled jobs | After three apps began filtering, four of seven beat tasks raised on every run. No test noticed: every task test ran inside a bound organization, which a worker never has. |
| Seed and demo commands | `seed_demo` rewrote another company's People department by upserting on a code that is unique only per organization; `seed_demo_company` renamed an arbitrary organization and hired demo staff into another; `--remove` deleted accounts by email domain across every customer. |
| Branding | The unauthenticated branding endpoint fell back to "the first organization", which is one customer's name and logo on another's login page. |

Each fix carries a test that fails without it, and the four most recent are
re-attempted live by the isolation report on every run.

## 7. Identity and authentication

`User.email` stays **globally unique**. Login goes through stock
`ModelBackend`, which requires a unique `USERNAME_FIELD`; per-organization
email would mean replacing the auth backend, changing `USERNAME_FIELD`, and
adding org discovery to a login page that has no user to derive an org from.

So one login belongs to one organization, derived from membership *after*
authentication — precisely the fail-closed ordering the incident requires.
Membership is modelled as a genuine many-to-many association
(`OrganizationMembership`) with a **V1 clamp**: a partial unique constraint
allowing one active membership per user. The schema permits multi-organization
membership; V1 forbids it.

**Dropping the clamp is the schema change, not the feature.** What follows is
real work: which organization a multi-org user lands in at login, an explicit
"active organization" concept and a switcher, JWT claims and their re-issue on
switch, the permission cache key, frontend query-cache partitioning, file
access, Celery targeting, audit attribution and notification routing. The
design makes that possible without redesign — the `(user_pk, requested_org_id)`
cache key and the membership table are the two pieces that would otherwise
force one — but it is a project.

**The cost, stated plainly:** if `alice@example.com` already has an account,
another organization's admin cannot invite her. That belongs in the product
documentation, not in a support ticket.

Two paths resolve a person before any organization exists, and both search
across organizations **on purpose**, because finding the organization is what
they are for: the personal-email login fallback (which refuses when an address
matches two active employees, in one company or two) and the public
application/interview-slot tokens, which are globally unique capabilities.

## 8. The platform layer

**Platform Admin is a structural flag** (`User.is_platform_admin`,
`editable=False`, set only by a management command), not a role. Role rows are
runtime-editable, so a platform resource in the permission matrix would let an
organization admin grant themselves platform authority.

**No implicit access to customer HR data, structurally.** A platform admin
holds no role grant in any organization, so `resolve_context()` returns
`DENY_ALL`, every tenant queryset resolves to nothing and `RBACPermission`
refuses every tenant route. It is a property of the object, not a policy
somebody enforces.

Everything lives under `/api/v1/platform/` with its own sign-in entrance, a
`platform_only` view declaration, and build checks that fail for a
platform-prefixed view without the flag, the flag outside that prefix, or both
flags at once.

**Organisation provisioning** is one atomic service: Organization → OrgSettings
→ Subscription → config seeds → admin user, membership and role grant →
invitation email on commit → audit rows. A failure at any step rolls the
organization back, so a retry is clean and there is no half-provisioned tenant.

**No operator entry point to provisioning.** `provision_organization()` is
complete, atomic and tested — and called from nothing but tests. The platform
console's organization viewset is **read-only**, and no management command
wraps the service, so creating a customer today means opening a Django shell.
The service is the hard part and it exists; the missing piece is a `POST`
route or a command, and until one lands "a platform admin creates an
organization" is true of the service and not of the product (§12).

**Not built: `SupportGrant`.** The design exists in the plan — a time-limited,
organization-approved, read-only grant whose scope comes from a code constant
listing config resources only. No code implements it. Today a platform admin
has no route into customer data at all, which is the safe end of that
trade-off, and any support access must be designed before it is shipped.

## 9. Plans, features and limits

`Organization → Subscription → Plan → Features + Limits`.

**Feature gating with no scattered checks**: a `FeatureCode` enum (11 features)
plus a total map from every `Resource` to exactly one feature, with a build
check that the map is total. One permission class reads the view's
already-resolved resource, so nobody writes a feature check anywhere and adding
a `Resource` without deciding its feature fails the build.

**Employee limits** are enforced in one service holding a `select_for_update()`
lock on the Subscription row — a bare `count()` is a TOCTOU hole where two
concurrent creates both read limit−1 and both commit. It raises 422 ("the
system will not allow this"), not 403 ("you may not").

**Two statuses, one authority.** `Organization.status` is what
`resolve_context()` reads; `Subscription.status` is commercial state and writes
the former through one service, so there is exactly one write path and no
divergence. Suspension is a DRF permission class, never middleware — a
middleware check would run before DRF resolved the JWT, see `AnonymousUser`,
and wave every suspended organization through, which is the 2026 shape exactly.

**A downgrade never deletes data.** Payroll records remain stored and
exportable while payroll *actions* return `feature_not_available`; the gate
reads the resolved action, so writes are refused and reads survive for a grace
window. A customer must be able to retrieve records they are statutorily
obliged to keep.

## 10. Per-organization configuration, files, email and background work

**Configuration**: `settings.X` is a default, not the value. Every resolver
takes an **explicit** `organization` — a `current_org()` convenience would be
the incident's shape again, and an explicit argument turns a forgotten call
site into a `TypeError` instead of a silent cross-tenant read. Fallback is to
settings, never to another organization, which keeps self-hosted and SaaS on
one code path. Secrets use the existing encrypted field, are `write_only`, and
read back as `has_password: bool` — never a masked value, never a reveal
endpoint.

**Files**: every organization's uploads live under
`media/organizations/<uuid>/…`. The path is *not* the security boundary —
downloads go through a view whose scoped `get_object()` is the authorisation
check — but the subtree makes per-tenant deletion a directory removal, makes
per-tenant bucket policies possible, and makes a cross-tenant path visible in a
bug report. A field-level test asserts every `FileField`/`ImageField` resolves
through the org-scoped path builder.

**Email**: per-organization SMTP, sender identity and templates, resolved with
the deployment's settings as fallback and never another organization's. No
recipient may cross organizations: every send resolves recipients from
org-scoped querysets, and a test asserts that no Org B action produces a
message addressed to an Org A employee. Retries carry their own stored
`organization_id` rather than reading ambient context.

**Celery**: each beat row names a **dispatcher** that queues one subtask per
running organization. Every subtask takes an `organization_id`, re-reads and
re-validates it, skips a customer suspended since dispatch, raises on an id
that does not resolve, and binds the organization for its body. Celery
serialises arguments, not context variables — a task assuming inherited context
would run under whatever the previous task on that worker left behind, which is
the fail-open shape on a worker instead of a request. One customer's
unreachable device server is one failed subtask with its own retry, not a loop
that dies at organization three; and creating a customer stays a pure database
operation rather than a write to the scheduler.

## 11. Audit and proof

Audit rows carry the organization, the actor and their email, the action,
resource, entity, timestamps, request id, and a field-level before/after diff
with per-model redaction. The log is append-only **in Python**: `save()` raises
if `pk is not None` and `delete()` always raises. `ARCHITECTURE.md` also
specifies `REVOKE UPDATE, DELETE ON audit_auditlog` from the application
database role; **no code in this repository performs that revoke** (§12), so
today the guarantee is one layer deep rather than two. Platform actions record the
*affected* organization with the platform admin as actor, which is what makes
"who suspended this customer, and why" answerable.

**A design point worth recording: an audit row takes its organization from the
actor, not from the affected entity.** That is what made the cross-tenant
offboarding defect visible — the row was stamped to the attacker's
organization, which is the honest attribution and also the evidence.

Proof, in three layers:

1. **The suite** — 2,177 passing across 127 files, including a cross-tenant
   route walker derived from the URL resolver (so a route added next year is
   covered the day it is added), a write-injection matrix, a per-model manager
   matrix, a Celery isolation matrix with the "handed another organization's
   object id must fail" case, and per-command isolation tests.
2. **The build** — `manage.py check` with 17 structural checks, run by the
   deploy entrypoint before boot.
3. **[`TENANT_ISOLATION_TEST_REPORT.md`](TENANT_ISOLATION_TEST_REPORT.md)** —
   generated by a script that provisions three organizations and attacks them
   from each other. 295 of 295 checks passed at `cd8932f`.

**One test fails on purpose.** `test_no_unresolved_statutory_disputes` is the
release gate for four unanswered statutory interpretation questions. It stays
red until Finance answers them against gazette sources. Do not make it pass.

## 12. What is not done

Stated plainly, because the gaps are the useful half of an audit.

| Gap | Status |
|---|---|
| **Employee import (Stage 5e)** | Not started. `ImportBatch` still requires a job opening and has no `kind` discriminator; there is no `EmployeeSpec`. Three traps are already identified: 200 imported employees currently fire 200 separate welcome emails each bounded by a 15-second SMTP timeout; the employee-code counter must be locked once per batch, not per row; and plan limits must refuse the **whole batch** rather than import a partial staff list. |
| **Frontend SaaS surface (Stage 6)** | Not started. No `hasFeature()`, no `/setup` or `/suspended` guards, no setup-wizard UI, no plan page, no platform console. Every backend endpoint they need exists. |
| **Demo data profiles (Stage 6)** | Not started. Healthcare / Technology / Retail at 20/5/3, 15/4/2, 10/3/2, on deliberately different plans so every SaaS mechanism is exercisable by hand. |
| **An operator entry point to provisioning** | Missing. The service is atomic and tested; nothing but tests calls it. The console lists organizations read-only and there is no `provision_organization` management command, so onboarding a customer requires a Django shell. |
| **Layer E: database composite foreign keys** | Not implemented. Raw SQL and bulk paths are covered by the manager and the stamping mixin, not by the database. |
| **`SupportGrant`** | Not implemented (§8). |
| **Database-level append-only audit** | `ARCHITECTURE.md` specifies `REVOKE UPDATE, DELETE ON audit_auditlog` from the application role. Nothing in this repository issues it — not a migration, not the deploy entrypoint. The Python guards hold, but a raw `UPDATE` would succeed. |
| **Postgres RLS** | Deliberately deferred, with the reason recorded above. |
| **Multi-organization membership** | Schema permits, V1 clamp forbids (§7). |
| **Statutory disputes** | Four open questions; the gate stays red (§11). |
| **The isolation script's own creation path** | It builds its three organizations by hand rather than through the provisioning service, which now exists. Pointing it at that service is the next improvement to the proof. |

## 13. Risks worth keeping in view

1. **The escape hatch is the audit surface.** 13 `all_orgs()` call sites in
   product code, each deliberate and each greppable. That number going up
   without review is the thing to watch — `grep -rn all_orgs` is the audit.
2. **The manager protects the ORM, not raw SQL.** Nothing in this design stops
   a future `cursor.execute()` from crossing organizations. Layer E and RLS are
   the answers, and neither is built.
3. **Tests bind an organization by default.** An autouse fixture binds one for
   every test, because hundreds construct models directly. That is what hid the
   broken scheduled jobs for three commits. Tests about unbound behaviour must
   opt out with the `unbound_organization` marker, and code that runs on a
   worker needs a test that does.
4. **Documentation drifts faster than code.** Three of the four documents
   updated alongside this one still asserted "there is deliberately no
   multi-tenancy" weeks after every table had carried the column.
